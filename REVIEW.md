# REVIEW.md

## Defects Found in Starter `app/main.py`

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (L33-37) | Replaces hour/minute directly on a naive or UTC `punch_in` datetime without converting to IST first. Also uses `minutes > 10` check on floating-point minutes, which fails on exact boundary cases (e.g. 09:40:01 yields 10 mins elapsed, but `10 > 10` returns False -> 0 late mins). Microseconds are not truncated. | A punch-in at 09:40:01 for a 09:30 shift returned 0 late minutes instead of 10. UTC timestamps shifted shift start calculations incorrectly. | Truncated `punch_in` to whole seconds, converted to IST timezone, computed total seconds elapsed past shift start, checked if `diff_seconds > 600`, and returned `int(diff_seconds // 60)`. |
| 2 | `compute_work_hours` (L40-41) | Uses Python's default banker's rounding (`round()`, round-half-to-even) instead of required half-up rounding (R4/R8). Microseconds are not truncated to whole seconds (R1). | Work hours ending in exact half cents (e.g. `2.675`) rounded down to `2.67` instead of up to `2.68`. | Truncated punch times to whole seconds, computed total seconds / 3600.0, and rounded using `Decimal` with `ROUND_HALF_UP`. |
| 3 | `compute_overtime` (L44-47) | Assumes `shift_end` is on the same calendar date as `date_str`, failing for overnight shifts (e.g. 22:00–06:00 where shift end is on the next calendar day). Returns overtime for any positive duration without enforcing the 30-minute minimum threshold (R3). | Overnight shift punch-out at 06:40 IST next day was compared against 06:00 on the start date (24h off). A 5-minute overtime returned 5 instead of 0. | Handled overnight shifts by setting `shift_end` date to the next calendar day when `shift_end <= shift_start`. Enforced that overtime is returned only when `overtime_seconds >= 1800` (30 mins). |
| 4 | `create_employee` (L78-85) | Relies on check-then-insert (`find_one`), causing race conditions under concurrent duplicate requests. Does not catch `DuplicateKeyError`. Does not validate `shift_start != shift_end`. | Concurrent POST requests with the same `emp_code` caused duplicate insertions or unhandled 500 errors. Setting `shift_start == shift_end` was allowed. | Created a unique database index on `emp_code`, caught `DuplicateKeyError` to return HTTP 409, and validated `shift_start != shift_end` (raising HTTP 422 if equal). |
| 5 | `list_employees` (L88-96) | Off-by-one pagination bug: `skip = page * page_size` skips page 1 completely (should be `(page - 1) * page_size`). `total` counts the whole collection rather than the filtered department query `q`. Missing required sort by `emp_code` ascending. | Requesting `page=1` returned items starting from index 21; `total` count ignored `department` filter; employee list order was nondeterministic. | Fixed skip calculation to `(page - 1) * page_size`, passed filter `q` to `count_documents(q)`, and added `.sort([("emp_code", 1)])`. |
| 6 | `punch_in` (L99-121) | Check-then-insert race condition on `(emp_code, date)` allows duplicate punch-ins. Ignores R1 overnight shift date calculation (`ts.date().isoformat()` misassigns 01:00 IST punch-in to the new day). Unknown employee raises `TypeError` -> 500 error instead of 404. Returned document includes `id: str(res.inserted_id)`, violating contract. `punched_at` timestamp converts without timezone awareness and lacks validation. | Concurrent punch-ins succeeded twice or raised 500; overnight punch-in created wrong date record; invalid/unknown employee returned 500 error; response contained forbidden `id` field. | Added compound unique index on `(emp_code, date)` and handled `DuplicateKeyError` -> 409; implemented R1 overnight shift date calculation; checked employee existence -> 404; validated `punched_at` bounds -> 422; stripped internal `_id` / `id` fields. |
| 7 | `list_attendance` (L124-150) | Loads all matching records into Python memory (`list(db.attendance_logs.find(q))`) before sorting and slicing, leading to memory/performance bottlenecks on ~100k records. Does not validate `date_from > date_to`. | High memory usage and slow responses on large datasets; passing `date_from > date_to` returned empty list instead of 422 error. | Pushed sorting `.sort([("date", -1), ("emp_code", 1)])`, skip, and limit directly to MongoDB; added validation raising 422 when `date_from > date_to`. |
| 8 | Missing Endpoints | Starter file omitted `/attendance/punch-out`, `/attendance/{emp_code}/{date}`, `/analytics/employees/{emp_code}/monthly`, `/analytics/departments/summary`, `/analytics/leaderboard/late`, `/analytics/departments/{department}/trend`, and `/admin/explain/{endpoint}`. | Requests to these endpoints returned 404 Not Found. | Fully implemented all required endpoints in `app/main.py` per `openapi.yaml` and `DATA_MODEL.md`. |

## Examined and Decided NOT a Defect

1. **Use of Plain String Dates (`YYYY-MM-DD`) in MongoDB**:
   - *Examination*: Looked at storing dates as string vs BSON Date.
   - *Decision*: Plain string date `"YYYY-MM-DD"` is explicitly specified in `DATA_MODEL.md` Section 1 ("Calendar dates and times of day are plain strings on purpose: a date is not an instant..."). It is the correct data model design.

2. **Storing Truncated UTC Instants in MongoDB**:
   - *Examination*: PyMongo returns BSON dates as naive datetimes by default.
   - *Decision*: Verified that storing BSON Date in UTC (truncated to whole seconds) and converting to/from epoch milliseconds at the API boundary conforms to the API contract.
